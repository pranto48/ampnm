# AMPNM Analysis + Windows Agent Build Plan + Docker Auto-Update Plan

## 1) Current AMPNM Docker App Analysis

### Current architecture observed
- `app` service is built from local `Dockerfile` and runs PHP/Apache app code mounted from the repo.
- `db` service is MySQL 8.0 with persistent `db_data` volume.
- App and DB configuration are injected from `docker-compose.yml` environment variables.
- Update awareness already exists (`AMPNM_ENABLE_UPDATE_CHECK_SCHEDULER` + interval), but there is no fully managed in-place auto-upgrade/rollback workflow.

### Operational gaps to address
1. No standard one-command update+rollback process.
2. No image pinning strategy for deterministic rollback.
3. No Windows-native monitoring agent to complement Linux agent assets.

## 2) Windows Client Agent App Plan

## Goals
- Provide host-level metrics and service telemetry from Windows endpoints to AMPNM cloud/functions.
- Match Linux agent feature parity where practical.
- Support silent install, service mode, secure updates, and enterprise deployment.

## Proposed stack
- Language/runtime: .NET 8 (Windows LTS friendliness, service support).
- Service host: Worker Service (`BackgroundService`) running as Windows Service.
- Packaging: MSI (WiX) + optional single-file EXE bootstrap installer.
- Metrics collectors:
  - CPU, memory, disk, uptime.
  - Optional process inventory.
  - Optional Windows event-log summaries.
- Transport:
  - HTTPS JSON to Supabase edge function endpoint (`agent-metrics` style contract).
  - API token/device key in Windows Credential Manager or encrypted DPAPI store.

## Client architecture
1. **Collector layer**: reads performance counters/WMI.
2. **Normalizer layer**: maps to existing AMPNM metric schema.
3. **Queue/retry layer**: local spool for offline buffering.
4. **Sender layer**: batched HTTPS with exponential backoff.
5. **Control layer**: polls for remote config (intervals, thresholds).

## Build phases
1. **P0 - Contract alignment**
   - Freeze JSON payload schema and auth mechanism.
2. **P1 - MVP agent**
   - Service install, CPU/memory/disk/uptime collection, send every 30-60s.
3. **P2 - Hardening**
   - Signed binaries, retry queue, structured logs, watchdog restart.
4. **P3 - Enterprise rollout**
   - Group Policy deployment, proxy support, offline installer.

## CI/CD for Windows agent
- Build on GitHub Actions Windows runners.
- Produce signed artifacts: `ampnm-agent-setup-x64.msi` and `.zip` portable.
- Publish release metadata JSON consumed by client updater.

## Needed to build (checklist)
- [ ] API contract doc for metrics ingestion.
- [ ] Device enrollment flow + token issuance.
- [ ] Certificate/code-signing pipeline.
- [ ] Installer UX/spec (interactive + silent mode).
- [ ] Release channel policy (stable/beta).

## 3) Docker App Auto-Update + Restore (Rollback) Plan

## Update strategy
- Add maintenance scripts for controlled updates:
  - `scripts/auto-update.sh` (snapshot state, optional DB backup, pull+recreate).
  - `scripts/rollback-update.sh` (re-tag prior images and redeploy).
- Keep rollback metadata under `.update-state/<timestamp>/rollback.env`.
- Backup policy: DB dump generated by default prior to update (can be disabled).

## Suggested production enhancements (next)
1. Pin image tags or digests in compose for deterministic rollback.
2. Add health-gate check after update (auto rollback on health failure).
3. Rotate/prune old update-state folders and stale backups.
4. Emit update audit log + alert notification.

## Operator runbook
- Update:
  - `./scripts/auto-update.sh`
- Roll back most recent update:
  - `./scripts/rollback-update.sh`
- Roll back specific snapshot:
  - `./scripts/rollback-update.sh ./.update-state/<timestamp>/rollback.env`
